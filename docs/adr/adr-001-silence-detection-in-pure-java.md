# ADR 001: 無音区間検出を純粋Javaで実装する

## Status

Accepted

## Context

English Drill Helperは、『英語のハノン』の付属音声のようなドリル音声を再生する。1つのファイルに多数の文が収められ、文と文の間は無音で区切られている。PRD（docs/prd.md）では、学習者がファイルを開いて文の一覧を見て、1文ずつ再生・繰り返すとしている。このため、アプリは無音区間を見つけてファイルをセグメントに分割しなければならない。

JavaFX Mediaはmp3・AAC・WAVを再生できるが、デコード後のサンプルを取り出す手段がない。したがって、解析のために音声をPCMサンプルとして読む別の経路が必要になる。

PRDの制約は次のとおり。WindowsとmacOSで動く。オフラインで動く。ドリル音声は同梱しない。利用者に必要なのはJavaとMavenだけで、JavaFXはMavenが取得する。ffmpegのようなネイティブツールを追加すると、最後の点が崩れるか、配布サイズが大幅に増える。

2026年8月28日に、Java 25で何が動くかを確かめる技術検証（使い捨ての実験コード）を行った。既知の位置に無音を入れた5.4秒のWAV（1.0〜1.5秒、2.5〜3.2秒、および無視されるべき0.2秒の無音）を生成し、ffmpeg 8.0でmp3とm4aに変換して、無音区間の検出を試した。結果はAlternativesとConsequencesに記す。

## Decision

無音区間の検出は、外部ツールやDSPライブラリを使わず、純粋Javaで実装する。

音声のデコードにはJava Sound API（javax.sound.sampled）を使い、16bit PCMに変換して読む。mp3のデコードには com.tianscar.javasound:javasound-mp3 1.9.8（JLayer/mp3spiの保守版）をJava SoundのSPI（Service Provider Interface。Java Soundが対応形式を追加するために用意している差し込み口で、jarをクラスパスに置くだけで自動的に認識される）として追加する。ファイルは File ではなく BufferedInputStream 経由で開く。File で開くとこのライブラリは0バイトしかデコードしない。PCMへの変換は、エンコーディング指定ではなく、明示的な AudioFormat（PCM_SIGNED、元のサンプルレート、16bit、元のチャンネル数、リトルエンディアン）を渡して行う。これらの作法はデコードを担当する1つのクラスに閉じ込める。

検出は自前のコードで行う。PCMを一定時間のウィンドウに区切り、ウィンドウごとの全チャンネルのRMSをdBFSに換算する。しきい値未満のウィンドウを無音とし、無音が最小無音長以上続く区間を区切りとする。区切りの間をセグメントとする。ウィンドウ幅・しきい値・最小無音長はパラメータとして外に出す。具体的な値はこのADRでは決めず、実際の教材音声で調整しながら実装時に決める。

対応する形式は当面 mp3 と WAV に限る。m4a/AACは対象外とし、必要になった時点で別のADRで決める。

## Alternatives

### 代替案1: ffmpegを外部プロセスとして呼ぶ（silencedetectフィルタ）

対応形式と検出精度は最も優れる。しかし利用者にffmpegのインストールを求めるか、バイナリ（LGPL、数十MB）をOSごとに同梱する必要がある。「JavaとMavenだけで動く」という前提を崩すため採用しない。開発機にはffmpeg 8.0があり、テスト用音声の生成には使う。

### 代替案2: bytedecoのffmpegバインディング（org.bytedeco:ffmpeg-platform 8.1.2-1.5.14）

Javaからffmpegを直接呼べる。しかしプラットフォーム別のネイティブライブラリで配布サイズが数十〜100MB規模になる。無音検出だけのためには過大なため採用しない。

### 代替案3: TarsosDSP

SilenceDetectorクラスを持つ純粋JavaのDSPライブラリ。しかしMaven Centralに公開されておらず、必要な処理（RMSとしきい値判定）は自前で数十行で書けるため採用しない。

### 代替案4: JavaFX MediaのAudioSpectrumListener

再生中に帯域ごとの音量を受け取れる。しかし実時間の再生中にしか値を得られず、ファイルを開いた時点で一覧を作る用途に合わないため採用しない。

### 代替案5: 旧来のmp3spiスタック（com.googlecode.soundlibs:mp3spi 1.9.5.4 + jlayer 1.0.1.4 + tritonus-share 0.3.7.4）

技術検証では File から開いても InputStream から開いても正しく動作し、回避策が不要だった。デコード結果はtianscar版と同一（209フレーム、最大振幅0.476）。しかし2016年を最後に更新が止まっており、依存が3つのjarに分かれる。保守されている方を選び、回避策は1クラスに閉じ込めることで対処する。

### 代替案6: m4a/AACも対象にする（com.tianscar.javasound:javasound-aac 0.9.8、JAADの保守版）

技術検証ではファイルを開いてPCM（ビッグエンディアン）に変換できたが、ffmpegでエンコードしたAACのデコード中に ArrayIndexOutOfBoundsException でクラッシュした。安定して使える見込みが立たないため、当面は対象外とする。

## Confidence Level

方式（Java SoundでPCMにして自前でRMS判定）についての確信度は高い。技術検証でWAVとmp3の両方で既知の無音を正しく検出し、10分のmp3を約1秒で処理できた。

ライブラリ（javasound-mp3）についての確信度は中程度。File で開くと動かない不具合があることから、別の不具合が見つかる可能性はある。ただしデコードを担当するクラスは1つなので、旧来のmp3spiスタックへの入れ替えは小さい変更で済む。

パラメータ（しきい値・最小無音長）についての確信度は低い。技術検証は合成音で行ったため、実際の教材音声（ノイズフロアや文中のポーズの長さ）では調整が必要になる。

次の場合にこの決定を見直す。実際の教材音声で、パラメータ調整だけでは文の境界を安定して検出できないと分かったとき。m4aなどmp3以外の形式の教材を扱う必要が出たとき。javasound-mp3が将来のJDKで動かなくなったとき。

## Consequences

良い結果。利用者は追加のインストールなしでアプリを使える。依存はjarが1つ増えるだけで、配布サイズはほぼ変わらない。検出ロジックは自前の短いコードなので、TDDでテストを書きやすく、パラメータを自由に調整できる。10分のファイルを約1秒で処理できるので、ファイルを開いたときにバックグラウンド（Task）で解析して結果を保持すれば十分。

悪い結果。当面はmp3とWAV以外の教材を扱えない。javasound-mp3の作法（InputStream経由で開く、明示的なAudioFormatを渡す）を守らないと、エラーにならずに0バイトしか読めないという分かりにくい壊れ方をする。この作法をデコードクラスのコメントとテストで守る。合成音のテストだけでは実用上の精度を保証できない。

中立な結果。mp3のエンコーダ遅延により、検出位置は元の音声より約50ms遅れる。文の境界は無音の中にあるので、セグメントの前後に余白を持たせれば実用上の問題はない。再生はJavaFX Media、解析はJava Soundというように、2つのデコーダを使う。テスト用の音声ファイルは、既知の位置に無音を入れたWAVを生成し、開発機のffmpegでmp3に変換して src/test/resources に置く。生成スクリプトは helpers/ に置く。
