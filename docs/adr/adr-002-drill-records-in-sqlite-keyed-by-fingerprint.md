# ADR 002: ドリルの記録をファイルの指紋をキーにSQLiteへ保存する

## Status

Accepted

改定（2026-09-06）: アプリ名を English Drill Player に変えたのに伴い、データベースファイルは ~/.english-drill-player/drill.db、上書き用のシステムプロパティは edp.drill.db に改めた。以下の本文は決定当時の名前のまま残す。旧フォルダの記録は移行しない。

## Context

English Drill Helperは、ドリル音声を再生した記録を残す。ストーリーマップ（docs/storymap.md）では、最終再生日時の確認を最初の記録とし、その先に完了チェック、苦手チェック、前回終えたドリルの次から始める機能が並ぶ。これらの記録は学習者が積み上げる資産であり、音声ファイルから再構築できない。音楽プレイヤーのメタデータキャッシュとは性質が違い、失うと困る。

記録は音声ファイルに確実に結び付いていなければならない。ところが、ファイルのパスは安定しない。ストーリーマップには音声フォルダを自由に登録する機能と2つ目以降のフォルダを追加する機能があり、フォルダの移動や改名は想定内である。現在の音声フォルダはDropbox配下にあり、Dropboxは同期の際にファイルを書き直すことがある。このとき内容は同じでも更新日時が変わる。教材を別のPCにコピーして使うことも考えられる。

PRD（docs/prd.md）の制約は次のとおり。WindowsとmacOSで動く。オフラインで動く。利用者に必要なのはJavaとMavenだけで、追加のインストールを求めない。

保存先について、このプロジェクトにはまだ永続化の仕組みがない。参考実装のsss-music-player（F:\JavaFXProject\sss-music-player、ADR 001）はSQLiteとjOOQでライブラリDBを持ち、リポジトリの構成、例外の翻訳、テストの書き方まで整っている。開発者はこの構成に慣れている。

対象は現在253ファイル、合計約530MBである。

## Decision

ドリルの記録はSQLiteのデータベースに保存し、jOOQで読み書きする。sqlite-jdbcドライバとjOOQをMavenの依存に追加し、jOOQのコード生成はsrc/main/resources/db/schema.sqlをDDLDatabaseで解析して行う。同じschema.sqlを実行時のテーブル作成にも使うので、H2の解析器とSQLiteの両方で通る書き方に限る。

ドリルの同一性は、ファイル内容全体のSHA-256で決める。これを指紋（fingerprint）と呼び、小文字16進文字列で表す。記録の主キーは指紋であり、パスは主キーに使わない。パスは起動時の走査結果として画面側が持ち、指紋との対応はメモリ上で保つ。ハッシュ関数はSHA-256に固定し、変更しない。

スキーマは1テーブルから始める。

```sql
CREATE TABLE IF NOT EXISTS drill (
  fingerprint VARCHAR NOT NULL PRIMARY KEY,
  last_played_at BIGINT NOT NULL
);
```

日時はUTCのエポックミリ秒をBIGINTで持つ。Javaではjava.time.Instantと往復し、表示用のローカル時刻への変換はpresentation層で行う。完了チェックや苦手チェックの列は、その機能を作るときにこのテーブルへ足す。

データベースファイルはユーザーホーム下の~/.english-drill-helper/drill.dbとする。システムプロパティedh.drill.dbで上書きでき、テストは一時フォルダのパスを指定してAppごと起動できる。

コード上の構成はsss-music-playerに倣う。domain/repositoryにインタフェースDrillRepository、repositoryに実装SqliteDrillRepository、domain/exceptionにUnrecoverableException派生のRepositoryExceptionを置く。実装はSQLExceptionとjOOQのDataAccessExceptionをRepositoryExceptionに翻訳し、jOOQの型を外に出さない。指紋の計算はdomain/serviceのインタフェースと、serviceのSHA-256実装に分け、走査時に各ファイルへ付与する。jOOQの生成コードには@Generatedを付け、NullAwayのTreatGeneratedAsUnannotatedで検査対象から外す。

## Alternatives

### 代替案1: propertiesまたはJSONの単一ファイルに保存する

新しい依存が不要で、内容を目で確認しやすい。しかし変更のたびにファイル全体を書き直す必要があり、記録の種類（完了、苦手、再生日時）が増えるほど扱いにくくなる。数百件の記録を部分更新する用途にはデータベースが向くため採用しない。

### 代替案2: 素のJDBCでSQLiteを使う

依存がsqlite-jdbcだけで済む。しかしSQLを文字列で書くため型の検査がなく、列名の変更に弱い。参考実装でjOOQの構成が整っており、コード生成の手間よりも型安全の利益が大きいと判断して採用しない。

### 代替案3: パスを主キーにする

最も単純で、ハッシュ計算が不要である。しかしフォルダの移動や改名、別PCへのコピーで記録が切れる。記録は再構築できない資産なので、この弱さは受け入れられない。

### 代替案4: パス＋サイズ＋更新日時で照合する

sss-music-playerのメタデータキャッシュと同じ方式で、ハッシュ計算が不要である。しかしパスの弱さは代替案3と同じであり、さらにDropboxの同期で更新日時が変わると同じファイルでも別物と判定される。キャッシュには十分でも、資産の鍵には不足するため採用しない。

### 代替案5: ID3タグを除いた音声フレーム部分だけをハッシュする

タグを書き換えても指紋が変わらない利点がある。しかしmp3とm4aでタグの構造が異なり、実装と検証の手間が増える。教材のタグを編集する予定はないため、当面は採用しない。必要になれば指紋の計算方法を変える新しいADRで扱う。

### 代替案6: 指紋のキャッシュ表を最初から持つ

パス＋サイズ＋更新日時から指紋を引く表を用意すれば、起動のたびの再計算を避けられる。しかし現状の規模ではSHA-256の全件計算が数秒以内に収まる見込みで、キャッシュの効果を測る前に作るのは早い。遅さが実測で問題になったときに足す。

## Confidence Level

保存先（SQLite＋jOOQ）についての確信度は高い。参考実装で構成と運用が実証されており、そのまま移せる。

指紋を主キーにすることについての確信度は中程度。パスより頑健であることは確かだが、教材のID3タグを編集したときに記録が切れる点と、起動時のハッシュ計算にかかる時間は、実際に使ってみないと影響が分からない。

次の場合にこの決定を見直す。起動時の指紋計算が体感で遅く、バックグラウンド化やキャッシュ表でも足りないとき。教材のタグを編集する必要が出て、指紋が切れる問題が現実になったとき。記録の種類が増えて1テーブルの列追加では収まらなくなったとき。

## Consequences

良い結果。フォルダの移動、改名、Dropboxの同期、別PCへのコピーを経ても記録が同じファイルに結び付く。記録の種類が増えても、drillテーブルに列を足すだけで対応できる。リポジトリ層の構成とテストの書き方を参考実装から引き継げるので、実装の迷いが少ない。

悪い結果。依存にsqlite-jdbcとjOOQが加わり、ビルドにコード生成の段階が増える。起動時に全ファイルのハッシュ計算が必要になり、いずれTaskでのバックグラウンド化が要る。教材のタグを書き換えると記録が切れる。CREATE TABLE IF NOT EXISTSは既存のデータベースに列を足せないので、列を追加するときはALTER TABLEを流す仕組みを用意する必要がある。開発中はデータベースファイルを消して作り直してよい。

中立な結果。~/.english-drill-helper/drill.dbが利用者のマシンに作られる。同じ内容のファイルが複数あれば同じ記録を共有する。一覧の要素はパスだけでなく指紋を持つ型（例: AudioFile record）に変わる。データベースが開けないときの扱いは、docs/plans.mdの例外処理タスクで決める。
